# 장르 기본형, 모듈, 페이지 나누기

기본형은 고정 목차가 아니다. 글에 맞게 순서를 바꿀 수 있고, 바꾸면 스펙에 이유를 한 줄 남긴다.
절과 문단마다 역할(정의, 예시, 반례, 증명 단계, 해석, 확인 자료)을 하나씩 정하고 앞뒤 이동 경로를 확인한다.

## 기능 글

한 기능을 깊게 판다. 순서는 다음이 기본이다.

1. **장면·문제** — 독자가 화면이나 로봇 동작에서 볼 수 있는 결과나 문제에서 시작한다. 이 글이 누구를 위한 것인지 밝힌다. (Riot)
2. **판단과 대안** — 어떤 제약에서 무엇을 골랐고, 검토한 대안과 버린 이유가 무엇인지. 시행착오가 있으면 순서대로 보인다. 결정 이유가 기록에 없으면 '확인 못 함'이고, 작성자의 분석은 분석이라고 밝힌다. (Figma)
3. **원리** — 그 선택이 왜 동작하는지. 선수 글의 개념을 이어 쓰고, 처음 나오는 개념은 정의한다.
4. **확인 자료** — 검증 조건, 방법, 전후 수치. 테스트, 측정, 모의 계산을 구분한다. (Discord)
5. **남은 문제** — 기대한 것, 확인한 것, 남은 것을 나눠 쓴다. (토스)

## 개념 해설

1. **질문** — 이 개념이 왜 필요한지 보이는 질문
2. **그림·직관**
3. **정의**
4. **식**
5. **숫자 예**

- 입문 글은 숫자 예를 먼저 둘 수 있다. 구체와 추상을 여러 번 오가도 된다.
- 예시 뒤에는 일반 원리로 돌아와 적용 조건을 밝힌다. 예: 좌표 숫자로 원점 이동의 상쇄를 보인 뒤, 일반식으로 같은 상쇄를 보이고 "원점만 옮겼다. 축을 돌리면 성분이 달라질 수 있다"로 적용 범위를 닫는다(블로그 「점과 벡터」).

## 모듈 (필요한 글에만 붙인다)

| 모듈 | 붙이는 때 | 검토자에게 넘길 것 |
| --- | --- | --- |
| 증명 | 수학 주장을 증명하거나 강한 한정사를 쓸 때 | 주장 근거 표의 수학 행, 가정·기호 정의 위치, 의무별 닫은 위치 |
| 알고리즘 | 절차나 복잡도를 말할 때 | 비용 모델(무엇을 1 연산으로 세는지), 최악·평균·상환 중 어느 기준인지, 점화식과 기저 조건 |
| 측정 | 실측값·로그·데이터를 쓸 때 | 데이터 경로, 측정 조건, 다시 계산하는 명령(`numbers.json`의 `cmd`) |
| 코드 | 코드를 보이거나 코드 동작을 설명할 때 | 실행 환경, 입력, 명령, 기대 출력. 코드가 매 단계 계산하는 값과 본문 설명의 대조 |
| 시각화 | 그림이 설명의 한 단계를 맡을 때 | 그림 스크립트, 그림마다 맡는 단계, 그림 속 숫자·레이블과 본문의 대조 |

해당 없는 모듈은 스펙에 `N/A — 해당 요소 없음`으로 남긴다.

## 목적과 독자 질문 순서

- 스펙에 목적을 한 문장으로 쓴다. 「독자가 X를 이해하고 Y를 구분할 수 있게 한다」 꼴이다.
- 스펙에 「독자의 질문 → 이 단계에서 얻을 답」 표를 두고 절 순서를 그 표대로 짠다.
- 문제를 먼저 세운다. 도입은 결과만 보이지 말고, 독자가 무엇을 궁금해해야 하는지(무엇과 무엇이 맞지 않는지)를 먼저 쓴다.
- 각 절은 정상 동작의 답을 먼저 닫는다. 오류 분석, 변경 이력, 검증 자료는 그 뒤에서 답을 돕는다.
- 출발 장면(사례)을 절 끝마다 다시 불러와 설명이 같은 결과물을 말한다는 것을 잇는다.

## 작성자 자료와 독자 본문

규칙을 다 지켜도 근거·검증을 모두 본문에 쌓으면 읽히지 않는다(외부 검토, 2026-11-11).

- 작성자가 확보해야 할 자료와 독자가 지금 읽어야 할 내용을 나눈다.
- 조사 경위, 커밋 시각, 테스트 함수 이름, 코드 줄 번호는 본문에서 빼서 사내 참고나 확인 자료 절 한곳에 모은다.
- 「기록에 없다」, 「확인하지 않았다」, 「다음 편에서」는 본문에서 반복하지 않고 끝 절 한곳에 모은다. 설계 이유처럼 읽힐 비교 바로 앞에만 한 번 밝힌다.
- 이력이 설명에 필요하면 본문에는 한 줄만 두고, 길면 별도 페이지로 뺀다.

## 기호

- 기호마다 우리말 이름을 붙이고 본문에서 함께 쓴다: 「캘리브레이션 행렬 $T_{rt}$」. 아래첨자만으로 구분하게 두지 않는다.
- 기호가 셋 이상이면 기호표(기호, 이름, 무엇에서 무엇으로, 어디서 오나, 녹화 중 바뀌나)를 처음 쓰는 곳에 둔다.

## 시각 자료

- 절(H2)마다 그림이나 도식을 하나 이상 둔다. 표는 시각 자료로 치지 않는다(사용자 판단 2026-11-20). `check_style.py`가 시각 자료 없는 절을 잡는다.
- 장치와 배치를 설명할 때는 실물 사진이나 CAD 그림을 먼저 두고, 개략도는 그다음에 둔다.
- 그림 속 글자는 게시 폭에서 14 px 이상이 되게 그린다(노션 본문 폭 약 700 px 기준).
- 값을 바꿔 가며 볼 때 이해되는 관계(각도·오차에 따라 경로가 바뀌는 것 등)는 슬라이더 같은 상호작용 그림을 검토한다. 노션은 HTML 파일을 실행하지 않으므로 공개 URL에 올려 임베드해야 한다.

## 페이지 나누기

- 본문(사내 참고 제외)이 약 8천 자를 넘거나 중심 질문이 둘 이상이면 나눈다. `check_style.py`가 분량을 센다.
- 나눌 때는 허브 페이지에 목적·전체 그림·하위 페이지 목록을 두고, 하위 페이지마다 질문 하나를 맡긴다.
- 어디서 나눌지는 길이가 아니라 중심 질문으로 정한다. 떼어 낸 쪽이 독립된 질문과 답을 갖고, 그것만 읽어도 이해되고, 앞 글에서 링크로 관계를 설명할 수 있을 때 나눈다.
- 중심 결론에 꼭 필요한 정의, 핵심 절차, 증명은 길어도 본편에 둔다.
- 다음 글로 넘긴 내용은 질문 장부에 '다음 글로 넘김'으로 적고, 본문에 넘긴다는 문장을 한 줄 둔다.
